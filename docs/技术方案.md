# CaloriesControl 技术方案

版本：0.2  
日期：2026-09-16  
决策：稳定自用，**不申请 Apple 开发者账号、不上架、不依赖 macOS/Xcode**  
形态：iPhone **主屏幕网页（PWA）** + 系统 **快捷指令** 读健康 + 手表用系统 **健身**  
日常怎么点：[iPhone使用说明.md](./iPhone使用说明.md)

不在本期：原生 iOS/Watch App、App Store、云账号、社交、跟练视频、医疗诊断、Android 独立壳（网页本身可用任意手机浏览器，但不保证读健康）

相对 v0.1 的变更：取消 SwiftUI / HealthKit / watchOS 自研；手表数据改为快捷指令回传；开发可在 Windows 完成。

---

## 1. 目标

### 1.1 产品目标

在自己的 iPhone 上形成 **饮食 + 健身闭环**：打开主屏幕「热量控制」就能看到当天指令。

- 饮食：**不吃 / 减量 / 加量**（落到食物或营养缺口）
- 训练：**练这个 / 休息 / 加一组 / 补有氧**（结合目标与手表已产生的锻炼）

不做成商店 App。苹果不允许免费账号长期安装带 HealthKit 的自签应用；本方案用系统快捷指令读健康，用网页承载日记和建议。

核心闭环：

```
个人资料 → 每日热量/蛋白目标
    ↓
快捷指令读取健康（Watch 活动消耗 + 锻炼）→ 回传到网页
    ↓
网页拍照记饮食（人工确认后入库）
    ↓
建议引擎输出当天指令
    ↓
主屏幕网页展示（无自研表盘）
```

运动中体验仍全部交给系统「健身」+ Apple Watch。

### 1.2 用户目标

| 角色假设 | 要完成的事 |
|---|---|
| iPhone + Apple Watch，自用 | 不交开发者费、不每周重装，长期能用 |
| 减脂 / 增肌 / 维持 | 每天知道吃的方向、练不练 |
| 中文饮食 | 建议中文，食物名可手改 |
| Windows 开发 | 能在本仓库改网页、部署后用 Safari 打开 |

### 1.3 成功标准（MVP 可验收）

1. 能录入年龄、性别、身高、当前体重、目标体重、目标类型（减脂/增肌/维持），关标签后仍在。
2. 能通过快捷指令把「今日活动消耗 + 今日锻炼摘要」写入网页；指令失败时能手填消耗。
3. 能拍照一餐，AI 给出热量/宏量草稿，用户确认后写入日记。
4. 首页在无聊天的情况下给出至少 1 条饮食指令 + 1 条训练指令，并展示摄入、消耗、缺口。
5. Safari「添加到主屏幕」后可当独立入口使用（无浏览器地址栏优先）。
6. 无账号可完整使用；Gemini Key 只存在本机浏览器存储。
7. 无 Key 时仍可用：手动记饮食 + 基于规则的建议。
8. **不要求**自研 Watch 组件、不要求 App Store、不要求付费开发者账号。

### 1.4 非目标

- 替代系统「健身」做 GPS/心率运动中体验
- 自研 watchOS App、表盘剩余热量、HealthKit 原生读写
- 申请 Apple Developer、上架、TestFlight
- 替代医院/营养师方案
- 多用户云同步、社交、商城
- 微信内置浏览器作为主入口（相机与存储不可靠）

## 2. 待实现功能

P0–P2 构成可在 iPhone 上日常用的 MVP；P3 补训练清单；P4 增强。原 v0.1 的原生 Watch / HealthKit 能力整体取消或改到快捷指令。

### 2.1 P0 基础资料与目标计算

| ID | 功能 | 说明 |
|---|---|---|
| P0-1 | 引导与个人资料 | 年龄、性别、身高、当前体重、目标体重、目标类型、活动水平 |
| P0-2 | BMR / TDEE | Mifflin-St Jeor；有体脂时可切 Katch-McArdle |
| P0-3 | 每日营养目标 | 热量按目标类型加减；蛋白按 kg 体重 |
| P0-4 | 本机持久化 | 浏览器 IndexedDB（日记）+ localStorage（资料/Key）；无服务器账号 |

### 2.2 P1 手表数据（快捷指令，不是 HealthKit SDK）

| ID | 功能 | 说明 |
|---|---|---|
| P1-1 | 快捷指令「热量控制-同步今日消耗」 | 读健康：今日活动能量（kcal）、今日锻炼列表（类型、时长、估消耗） |
| P1-2 | URL 回传 | 指令结束后打开 PWA，查询参数或 hash 带上快照，网页写入 `HealthDayCache` |
| P1-3 | 手填降级 | 同步失败时，对照系统健身活动环手填今日消耗；锻炼可写「已跑步 30 分钟」等短句 |
| P1-4 | 权限说明页 | 网页内写清：为何要装指令、第一次会弹出健康权限 |
| P1-5 | 能量目标策略 | 默认 TDEE 用资料活动水平；可选「用近几次同步的消耗均值」校正（P3） |

网页 **不能** 自己读 HealthKit。唯一官方自用桥梁是系统快捷指令。

### 2.3 P2 拍照饮食

| ID | 功能 | 说明 |
|---|---|---|
| P2-1 | 拍照 / 相册 | `input capture` / 文件选择；单张起步 |
| P2-2 | 视觉识别 | 浏览器直连 Gemini（BYOK），JSON：菜名、克数、热量、蛋白/碳水/脂肪、置信度 |
| P2-3 | 确认编辑 | 改名称、克数、餐次；保存前预览对当日目标的影响 |
| P2-4 | 饮食日记 | 按日列表、删除 |
| P2-5 | 无网/无 Key 降级 | 手动输入名称与热量 |

须用 Safari 或主屏幕图标。微信/其他内置浏览器不做保证。

### 2.4 P2 建议引擎（产品核心）

| ID | 功能 | 说明 |
|---|---|---|
| P2-6 | 饮食指令 | `不吃` / `减量` / `加量` |
| P2-7 | 训练指令 | `按计划训练` / `休息` / `力量加量` / `补低强度有氧` / `缩短训练` |
| P2-8 | 规则引擎 | 无 LLM 也能出指令 |
| P2-9 | LLM 润色 | 只改中文 `detail`，不得改 `action`、不得突破安全约束 |
| P2-10 | 首页 Today | 目标 / 已吃 / 手表消耗 / 指令卡片 / 今日锻炼摘要 |

### 2.5 P3 训练清单（网页侧，不是 Watch App）

| ID | 功能 | 说明 |
|---|---|---|
| P3-1 | 计划模板 | 减脂 3 日、增肌 4 日、维持全身；生成一周勾选清单 |
| P3-2 | 打卡 | 网页勾选完成；与快捷指令带回的锻炼去重（已有跑步则不推同等有氧） |
| P3-3 | 动作库精简 | 40–80 个常用动作名称即可 |
| P3-4 | 主屏幕独立窗口 | Web App Manifest + Apple 相关 meta，减少 Safari 工具栏 |
| P3-5 | 与系统健身分工 | 运动中只用手表健身；网页只合并事后数据 |

**不做：** watchOS 工程、表盘组件、向 HealthKit 写回饮食。

### 2.6 P4 增强（明确延后）

- 多图同餐、语音记食物
- 自适应热量、完整多轮 Coach
- 条码、食谱、日记导出/备份
- 付费开发者账号后的原生 App（仅当用户改变约束时再开新方案）

### 2.7 建议引擎输入 / 输出（合同）

与 v0.1 相同。`watchActiveKcal` 与 `workouts` 来自快捷指令回传或手填，不来自 HealthKit SDK。

**输入（DailyContext）**

- 资料与目标热量/蛋白
- 当日已记录摄入
- 当日活动消耗与锻炼列表
- 近 3 日训练负荷（若有缓存）
- 当前时刻（决定下一餐）

**输出（DailyAdvice）**

```json
{
  "diet": [
    {
      "action": "reduce",
      "target": "晚餐油脂",
      "detail": "今日已超目标 280 kcal，晚餐改清蒸，少油少糖",
      "reason": "intake_over_target",
      "priority": 1
    }
  ],
  "training": {
    "action": "follow_plan",
    "title": "下肢力量 45 分钟",
    "detail": "手表今日尚无高强度锻炼，按计划练腿",
    "reason": "planned_session_pending"
  },
  "numbers": {
    "targetKcal": 2100,
    "foodKcal": 1680,
    "watchActiveKcal": 420,
    "remainingKcal": 420,
    "proteinG": 72,
    "proteinTargetG": 110
  }
}
```

`action` 枚举固定。LLM 只写 `detail`。

**快捷指令 → 网页 回传约定（P1）**

```
https://<部署域名>/#/sync?activeKcal=420&workouts=<url-encoded-json>&date=2026-09-16
```

`workouts` 示例：`[{"type":"running","minutes":32,"kcal":280}]`。网页校验日期为当天后再写入，防止旧链接。

## 3. 方案架构

### 3.1 总体架构

```
┌──────────────────────────────────────────────────────────┐
│  iPhone 主屏幕「热量控制」  PWA（Safari / standalone）      │
│  今日 / 饮食 / 训练 / 我的                                 │
└────────────┬───────────────────────────┬─────────────────┘
             │                           │
┌────────────▼────────────┐   ┌──────────▼───────────────┐
│  领域层（TypeScript）    │   │  接入层                   │
│  GoalMath               │   │  IndexedDB / localStorage │
│  AdviceEngine 规则优先  │   │  GeminiClient（浏览器直连）│
│  FoodAnalysis           │   │  ShortcutSync（解析 URL）  │
│  WorkoutPlanner         │   └──────────▲───────────────┘
└────────────▲────────────┘              │
             │            DailyContext   │
             └───────────────┬───────────┘
                             │
     ┌───────────────────────▼──────────────────────────┐
     │ 系统：快捷指令（读健康）→ 打开 URL                  │
     │ 健康 App 数据仓 · 健身 App · Apple Watch            │
     │ Gemini API（仅识别/润色，用户自己的 Key）            │
     └──────────────────────────────────────────────────┘
```

原则：

1. **无自建后端、无苹果开发者账号。** 静态网页托管即可。
2. **规则优先、模型辅助。** 与 v0.1 相同。
3. **健康数据只经系统快捷指令。** 网页不声明 HealthKit。
4. **确认后才落库。** AI 热量必须人审。
5. **运动中不自造体验。** Watch 只用系统健身。

### 3.2 仓库模块（Windows 可开发）

```
web/                 # Vite + TypeScript 前端（无 React，见 docs/实现说明.md）
  src/
    features/today|food|workout|profile|sync
    domain/          # GoalMath / AdviceEngine / FoodAnalysis（M1 起）
    data/            # IndexedDB、ShortcutSync（M1/M2）
    gemini/
  public/
    shortcuts/       # 快捷指令安装说明与签名后的导出指引
    manifest.webmanifest
```

领域层单测可用 Vitest，与 UI 分离。M0 已建好 Tab、Manifest、`#/sync` 占位。

不建 Xcode 工程，除非将来单独开「原生 App」新版本方案。

### 3.3 数据模型（IndexedDB）

| 实体 | 关键字段 |
|---|---|
| `Profile` | sex, birthDate, heightCm, weightKg, targetWeightKg, goal, activityLevel, proteinGPerKg |
| `FoodEntry` | date, mealType, name, grams, kcal, protein, carbs, fat, source(photo/manual) |
| `HealthDayCache` | date, activeKcal, workoutsJSON, source(shortcut/manual), fetchedAt |
| `WorkoutPlanDay` | date, title, itemsJSON, status |
| `AdviceSnapshot` | date, generatedAt, dietJSON, trainingJSON, numbersJSON, engineVersion |

Gemini Key **不进** IndexedDB 明文备份文件；放 `localStorage` 由设置页管理，界面可一键清除。

M3 实现：饮食日记与健康日缓存一样先放 `localStorage`（按日 JSON，约 21 天）；识别未确认草稿放 `sessionStorage`。IndexedDB 留待日记变大或导出再迁。

`AdviceSnapshot` 按日缓存。饮食或同步消耗变化时失效。规则重算便宜；LLM 润色节流。

### 3.4 关键流程

**A. 打开今日**

1. 读 Profile → GoalMath。
2. 读当日 `HealthDayCache`（可能过期，按钮「同步手表」）。
3. 汇总 FoodEntry → AdviceEngine 规则出卡片。
4. 有 Key 且快照过期 → 异步润色 `detail`。

**B. 同步手表**

1. 网页 `window.location` 跳到 `shortcuts://run-shortcut?name=热量控制-同步今日消耗`（名称冻结，改名则文档同步改）。
2. 指令读健康，再 `Open URL` 回 PWA `#/sync?...`。
3. 网页解析、校验日期、写入缓存、回到今日。
4. 用户取消或失败 → 提示手填。

**C. 拍照记食物**

1. 压缩图（最长边 ≤ 1280）→ Gemini JSON。
2. Review 改克数（热量按比例）。
3. 写 FoodEntry，建议快照失效。

**D. 训练**

1. 网页生成周清单。
2. 若同步结果已有 ≥30 分钟同类锻炼 → 指令改为恢复，不叠加。
3. 运动执行只在手表健身里发生。

### 3.5 建议规则（第一期写死）

饮食：

- 已摄入 > 目标 + 150 kcal → `reduce` 或 `avoid`
- 蛋白 < 目标 70% 且未到最后一餐 → `increase` 蛋白
- 下一餐将至且剩余很少 → `reduce` 主食或油脂
- 高强度后 2 小时内 → 允许 `increase` 碳水，不鼓励大赤字

训练：

- 计划未完成，且近 48h 无高强度 → `follow_plan`
- 当日已有 ≥30min 有氧或力量（来自同步）→ 不叠加同类；减脂可保留步行
- 连续 3 日高强度 → `rest` 或 `shorten`
- 减脂且消耗明显偏低、饮食已达标 → `easy_cardio`

安全约束（LLM 不可覆盖）：

- 不建议长期远低于 BMR × 1.1 的摄入
- 不给疾病医疗结论
- 年龄 &lt; 18 只维持，不做快速减重话术

### 3.6 API 与托管

| 对端 | 用途 | 数据离开设备 |
|---|---|---|
| 静态托管（GitHub Pages / Cloudflare Pages 等） | 下发 HTML/JS | 无用户日记（日记在浏览器） |
| Google Gemini | 食物图、润色 | 照片与结构化上下文；Key 在本机 |
| 系统快捷指令 / 健康 | 消耗与锻炼 | 不经本项目服务器 |

无账号系统。清站点数据即丢日记（P4 再做导出）。

### 3.7 安全与隐私

- Key 只存在本机浏览器，不提交 git、不进服务端。
- 照片默认不上传到自建服务器；识别后可不保留原图。
- 快捷指令仅读用户授权的健康类型。
- 页面声明：估算非医疗建议。
- 不走 App Store 审核；仍避免误导为医疗器械。

## 4. 实现依赖

### 4.1 硬性环境

| 依赖 | 用途 | 说明 |
|---|---|---|
| Windows 或任意能跑 Node 的电脑 | 开发、单测、构建 | **不需要 macOS / Xcode** |
| Node.js 20+ | Vite 工程 | — |
| iPhone + Safari | 主屏幕网页、相机 | iOS 16.4+ 即可（PWA 与快捷指令较稳） |
| Apple Watch（推荐） | 活动与锻炼写入健康 | 无表可手填消耗，建议变弱 |
| 系统「快捷指令」「健康」「健身」 | 读消耗、记运动 | 自带，无需开发者账号 |
| HTTPS 静态托管 | 相机、主屏幕、指令回跳 | 本地 `http` 在真机上不可靠 |
| Gemini API Key（可选） | 拍照识别 | 无 Key 则手动记账 |

**不需要：** Apple Developer Program、Xcode、Mac、TestFlight、付费证书。

### 4.2 技术栈

| 技术 | 用途 |
|---|---|
| TypeScript + Vite | 网页 |
| 原生 CSS 或轻量方案 | UI；不强制 React，选定后写进实现说明 |
| IndexedDB | 日记与缓存 |
| Web App Manifest + apple-mobile-web-app meta | 主屏幕独立窗口 |
| Vitest | GoalMath / AdviceEngine |
| 系统快捷指令 | 健康桥 |

浏览器直连 Gemini，无后端 BFF。注意 Key 会出现在该机网络请求中（用户自用可接受）。

### 4.3 第三方

| 依赖 | 用途 | 约束 |
|---|---|---|
| Gemini（Google AI Studio） | 视觉 + 润色 | BYOK，额度会变 |
| 托管商 | 静态文件 | 选免费档即可 |
| 无登录、无统计 SDK | — | 与自用、隐私一致 |

不自训食物模型。动作库第一期内置 JSON。

### 4.4 公式（GoalConfig，禁止散落魔法数）

- BMR（Mifflin-St Jeor）：男 `10w+6.25h-5a+5`，女 `10w+6.25h-5a-161`
- TDEE：BMR × 1.2–1.9，或同步消耗均值（P3）
- 减脂：TDEE − 300～500，下限 `max(BMR×1.1, 性别保守值 1200/1500)`
- 增肌：TDEE + 200～300
- 蛋白：1.6–2.2 g/kg

### 4.5 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 快捷指令被 iOS 改名/权限模型调整 | 同步中断 | 手填；文档教用户重装指令 |
| 回跳 URL 被截断或二次确认 | 体验差 | 短参数；失败明确手填 |
| 拍照热量误差 | 建议失真 | 强制确认；低置信度改手动 |
| 清 Safari 数据丢日记 | 数据没了 | 设置页警告；P4 导出 |
| 微信内打开无相机 | 以为坏了 | 使用说明强制 Safari / 主屏幕 |
| Gemini 额度 | 不能拍 | 规则 + 手动入口始终在 |
| PWA 不像原生 App | 心理预期 | 使用说明写清差别；不承诺表盘 |

## 5. 工作计划

单人、Windows 可全程开发。真机验收只需要 iPhone（及可选 Watch），用 Safari。

### 5.1 阶段与产出

| 阶段 | 周期 | 产出 | 依赖 |
|---|---|---|---|
| M0 网页脚手架 | 1 天 | Vite 工程、Tab、Manifest、部署空站 | Node |
| M1 资料与目标 | 2 天 | 资料页、GoalMath、Vitest | M0 |
| M2 快捷指令同步 | 2–3 天 | 指令 + `#/sync` 解析 + 手填 | M1、iPhone |
| M3 拍照饮食 | 3 天 | 相机、Gemini JSON、Review、日记 | M1、Key |
| M4 建议引擎 + 今日 | 3 天 | 规则卡片、润色、快照 | M2+M3 |
| M5 训练清单 | 2 天 | 周模板、与同步锻炼去重 | M4 |
